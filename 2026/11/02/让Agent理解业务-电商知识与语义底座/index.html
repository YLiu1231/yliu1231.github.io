让 Agent 真正理解业务：从文档检索到电商知识与语义底座

发表于 2026-11-02 分类于 Tech
电商 Agent 要可靠判断商品、权益、规则和实时状态，需要把文档检索、业务对象、结构化查询与实时接口组织成可追溯、可评价、可运营的知识服务。

一个电商运营人员希望 Agent 判断：这批商品能否使用某项优惠券，并与另一项权益组合。

回答这个问题，需要识别准确的商品集合和权益对象，找到适用渠道、人群与有效期，检查组合规则，必要时再查询当前业务状态。即使检索到了相关说明文档，其中缺少的适用条件、已经变化的状态，也足以让最终判断出错。

当 Agent 开始参与营销策划、用户体验分析和运营配置，企业知识服务就需要承担更多责任：解释业务含义，连接分散的证据，获取当前事实，并为后续动作提供可校验的依据。文档解析、切片和向量检索仍然重要，但需要放进一套更完整的技术体系中。

本文结合企业落地案例、官方技术文档和开源实现，讨论一种适合电商场景的方向：围绕业务对象组织知识，让文档检索、结构化查询和实时业务接口协同工作，再通过评价与版本管理维持知识质量。

业务含义，在哪里丢失

业务知识通常分散在不同载体中。商品属性存在主数据里，权益规则存在制度和系统配置中，用户体验问题存在原声与工单里，营销效果存在报表和复盘材料中。业务人员能够完成任务，是因为他们知道这些信息之间的联系，也知道哪些材料只是参考、哪些系统才是最终依据。

如果把所有内容转换成文本，再统一切片和向量化，这些联系可能在加工过程中丢失。

一张商务表格被拆开后，金额仍然存在，列名和适用条件却不在同一个片段中；一段工单保留了问题描述，处理过程与解决方案落在另外几个片段里；两份活动材料使用相同名称，却对应不同批次。模型找到的内容在语义上相关，未必适用于当前任务。

这种差异在电商分析中尤其明显。“最近一个月反馈最多的问题及其占比”，需要确定统计范围、时间窗、去重方式和分类口径，再查询总体数据。向量检索返回的几十条相关原声，可以作为说明问题的证据，却不能直接充当统计总体。

因此，知识底座需要保留三种联系：材料内部的结构，业务对象之间的关系，以及证据与适用条件之间的对应。检索算法的作用，是在这些信息得到妥善表达之后，把当前任务真正需要的内容找出来。

落地案例揭示了什么

LinkedIn 的客服实践提供了一个清楚的例子。公司作者在 2024 年发表的论文中，将历史工单组织成工单内部的树状结构和跨工单的关系图，通过规则与模板约束的 LLM 解析材料，再按问题检索相关子图。论文报告，生产环境随机分组对照中，工单解决时间中位数从 7 小时降至 5 小时，下降 28.6%。研究没有充分披露样本规模和显著性，仍需保留这一限制。论文全文

这个案例对电商服务的启发，是保留原声、体验问题、处理过程和解决建议之间的结构。已有的业务关系可以帮助系统找回更完整的依据；图谱是否有价值，应通过问题解决效果判断。

Uber Genie 的改进则展示了知识生产链的另一面。团队针对 40 多份安全与隐私政策、100 多道专家测试题，同时改进表格保真、元数据增强、来源路由、BM25 与向量检索，以及自动评价。文章报告，可接受答案比例相对提高 27%，错误建议相对减少 60%。这两个数字来自指定测试集，不能外推为全公司业务效率的提升。Uber 工程文章

对商务材料而言，这种改进方式很有借鉴意义。表格的行列关系如果已经在解析时丢失，后续检索很难准确找回完整条件。材料质量、检索范围与评价标准，需要一起设计。

电商知识结构化还可以参考 Amazon 的实践。AutoKnow 将现有分类、商品目录和行为数据结合起来，处理分类扩展、属性发现、补全、清洗及同义词归并。2020 年的官方文章报告，消费品图谱事实量增加接近 200%，商品类型识别准确率为 87.7%。这些数字反映知识覆盖与识别效果，不能解释为销售收益。Amazon Science

后续 COSMO 进一步将用户行为背后的意图纳入知识生成，通过人工标注和质量筛选构建知识，并报告已应用于搜索导航及线上 A/B 实验。它提示了一项值得研究的能力：连接消费者的表达、需求和商品属性，同时保留模型推断与已确认事实的区别。COSMO，SIGMOD 2024

这些案例解决的问题并不相同，却共同强调了业务结构、加工质量和验证。单独增加一个模型或图数据库，无法替代这几项工作。

知识结构化，应从哪些资产开始

电商知识体系可以围绕七类关联资产组织。它们描述的是需要管理的业务含义，并不要求分别建设七套系统。

资产 应当明确的内容 示例
术语与分类 标准名称、别名、上下位关系和定义 消费者所说的“券用不了”，对应哪类权益使用问题
业务对象与关系 对象标识、属性、关系和权威来源 商品、活动、优惠券及配置草稿之间的联系
规则与条件 适用范围、前提、例外、优先级和有效期 某项权益对渠道、人群及商品的要求
指标口径 公式、粒度、时间窗、过滤和归因方式 ROI 是否扣除退款、营销成本包含哪些项目
证据与经验 来源、结论、适用条件和验证状态 白皮书条款、用户原声、已确认的处理案例
动态事实 当前值、状态、查询时间和变更记录 库存、配置生效状态、审批结果
动作与完成标准 输入输出、前置条件、权限和核验方式 创建草稿、校验权益、确认配置是否生效

这套结构有几个需要特别处理的地方。

对象应尽量复用业务系统中的稳定标识。同名活动、不同规格商品、不同批次优惠券，不能仅凭文本相似度合并。跨系统标识存在差异时，需要维护映射；无法确定的关联应保留为候选。

规则必须携带适用条件和时间。一条描述只有与商品范围、渠道、地区、人群和有效版本结合起来，才可能支持准确判断。规则生效时间与系统收到更新的时间也可能不同，追溯设计需要考虑这种差异。

证据应保留其性质。用户说“价格变贵了”，记录的是用户感知；模型标注“负面情绪”，记录的是模型判断；实际成交价格则由业务系统提供。它们可以相互关联，但可信程度和用途不同。个人确认过的经验，也需要经过相应流程，才能成为组织共享知识。

指标定义同样需要独立维护。分析历史营销活动时，如果退款、成本和归因口径不一致，即使每条 SQL 都能执行，比较结果仍然可能失真。已有指标语义层和权威定义应被直接复用。

在表达方式上，可以借鉴 SKOS 的概念与标签机制、SHACL 的约束校验思路，以及 PROV 的来源表达。具体采用 JSON Schema、关系表还是图模型，应由查询与治理需求决定。

架构师的交付也应随之扩展：除了对象和术语定义，还需要提供关键关系、规则及指标口径、权威来源映射，以及一组必须回答正确的业务问题。用真实问题检查语义模型，才能发现定义是否足以支持工作。

技术底座如何组织

知识技术底座需要同时支撑知识生产与在线使用。前一条链路把分散材料加工为可发布、可追溯的知识资产，后一条链路根据任务选择信息来源，组合证据与实时事实。评价和运营贯穿两条链路，使使用中暴露的问题能够回到知识加工与发布环节。

下面是一种面向电商任务的逻辑架构。图中的模块表示职责，可以由现有系统、开源组件或自建服务共同承担。

  • 知识生产链：文档、表格、主数据与用户反馈 → 接入与解析 → 语义加工 → 知识资产管理 → 全文、向量、对象关系与摘要等派生检索表示。
  • 在线服务链：任务问题、业务对象与用户权限 → 查询规划与路由 → 派生检索表示及权威业务系统 → 证据组织 → Agent 与领域 Skills。
  • 反馈闭环：Agent 任务结果 → 任务验证、问题归因与回归评测 → 返回语义加工与知识发布环节。

知识生产链维护内容及其来源依赖；在线链路继承用户权限，读取已经发布且适用的知识，并查询需要实时确认的事实。实时业务数据保留在权威系统中，业务动作仍由相应接口执行。

接入与解析：保留结构，再生成片段

接入阶段应保留原件和可追溯的中间表示。表格需要保留表头、行列关系和脚注，流程需要保留步骤与分支，政策需要保留章节与适用条件。原生表格、HTML 或接口字段可以直接读取时，应优先利用这些结构。对用户反馈，则要保留原始表述，并把情感、观点等模型标签作为关联的加工结果。

Docling 的统一文档表示、结构分块和 token 感知的 HybridChunker，是这一层可以考察的开源能力。其分块机制支持在表格拆分后重复表头。具体材料是否解析正确，仍需检查；代码许可与所用模型许可也应分别核对。Docling 分块机制、官方仓库

切片之后保留多少上下文，需要通过评价确定。Anthropic 的 Contextual Retrieval 实验为片段补充上下文，并结合 BM25 和重排，报告 top-20 检索失败率从 5.7% 降至 1.9%。下降 67% 指失败率的相对变化，不能解释为答案准确率增加 67 个百分点，也不能直接据此确定其他业务的最佳切片参数。实验说明

语义加工：将材料与业务定义连接起来

语义加工包括术语归一、对象识别、单位和时间标准化、关系抽取、规则条件提取及冲突检查。已有业务系统明确提供的字段和标识，应直接使用；模型可以辅助处理非结构化材料，提出候选映射，再由程序或责任人校验。

架构师定义的对象、术语和关系，应当进入这一加工过程。例如，抽取权益条件时，需要识别条件属于哪一种权益、针对哪些商品和人群、在哪个时间范围内成立，并将结果关联到原文。存在同名对象、条件冲突或证据不足时，应保留待确认状态，避免在加工阶段将不确定性隐藏起来。

加工工具需要支持查看原文与抽取结果、修改映射、检查约束和重新处理。每次纠正都应能定位到对应的材料与规则，便于同类问题复用处理方法。

分层存储：区分知识资产与派生索引

不同信息有不同的生命周期，存储应按职责分工。

存储职责 主要承载内容 设计要点
原始材料与解析产物 原件、结构化文档、页码、段落及表格定位 保留来源，支持重新加工和原文核对
知识资产与元数据 对象定义、规则条件、版本、权限、责任人及审核记录 管理哪些知识已确认、已发布，以及适用范围
全文与向量索引 用于搜索和相似度匹配的表示 可由源材料及语义资产重建，记录生成版本
关系存储 对象关联、跨文档关系、证据依赖 按查询需求选择关系表或图存储，保留关系来源
权威业务系统 当前价格、库存、资格、配置状态及执行结果 通过接口查询或受控快照使用，标明时效

统一语义访问不要求统一物理数据库。是否引入独立图数据库，应取决于关系遍历、数据规模和维护需求；部分对象关联可以通过关系表与受控查询完成。向量和自动抽取图不应成为知识的唯一存放位置，否则更换模型或重建索引时，可能连同已经确认的业务含义一起丢失。

查询与检索：按问题类型选择路径

在线查询首先需要明确用户要查哪个对象、什么时间范围，以及需要解释、统计还是状态确认，再选择相应的信息获取方式。

问题类型 主要查询路径 返回结果应携带的依据
查询白皮书或操作指南 文档混合检索、重排与上下文扩展 原文、版本、适用条件
查询商品或活动属性 对象标识与结构化查询 对象 ID、字段含义、权威来源
确认配置是否生效 实时业务接口 查询时间、实际状态
查找相关体验问题 结构化过滤、关系查找与原声检索 分类依据、反馈出处及关联对象
分析主要问题及占比 确定范围的聚合分析，再取代表性证据 总体范围、分母、去重及时间口径
判断权益适用或组合条件 对象与规则查询，结合必要的文本证据 适用条件、例外及规则核验结果

全文检索适合准确术语和编号，向量检索帮助匹配不同表达，关系查询补足对象之间的联系。召回后可以融合候选结果、重排、去重，并恢复必要的章节或表格上下文。权限、有效期和发布状态需要贯穿查询及结果返回过程，不能留给生成模型自行判断。简单问题可以走明确路径，只有确有需要的复杂问题才进入多轮检索与推理。

Elastic 提供全文、向量、融合及重排能力，BGE-M3 提供稠密、稀疏和多向量检索表示。这些组件可以组成检索链路，但是否带来增益，取决于具体数据、版本与配置，仍需通过业务问题集检验。Elastic 文档、BGE-M3 官方说明

服务输出：让 Agent 获得可追溯的结果

最终提供给 Agent 的结果，应当说明它对应哪个对象、来自哪里、适用什么条件、采用哪个版本，以及还有哪些信息缺失。动态事实还需要附带查询时间，模型推断需要与已经确认的内容区分。存在冲突时，应返回冲突依据，交由明确的规则或责任人处理。

MCP 或普通 API 可以承载这种服务接口，业务语义与质量保证则需要在接口背后实现。上层 Agent 负责结合任务目标组织工作，知识服务负责提供可用依据，业务接口负责规则核验和实际操作。这样的职责划分，使不同 Agent 和 Skills 可以复用同一套知识服务，也便于分别评价检索、推理与执行的效果。

可运营，意味着知识变化后仍然可信

知识服务上线后，真正持续发生的工作是更新。政策会调整，活动会结束，商品会下架，材料会被撤回，模型和解析器也会升级。平台必须知道这些变化影响了哪些结果。

Ring 的公开案例将知识入库评价与生产发布分开，按地域元数据限制检索，并提供版本回退。文章报告新增 locale 的扩展成本减少 21%，属于客户与供应商自报的成本效果。这一案例更值得借鉴的部分，是把知识更新作为有验证、有发布状态的过程管理。Ring 与 AWS 联合案例

对企业知识服务，可以区分候选、待确认、已发布和已失效等状态。内容、解析策略、抽取模型和索引发生变化时，应能比较影响，并在出现问题时回退。删除一份文档，还需要处理它所派生的片段、关系、摘要和缓存，防止已撤回的材料继续作为有效依据。

权限也需要沿知识加工和使用链路传递。用户能够接入某个系统，不代表可以读取其中全部材料；检索、关系扩展、缓存和引用返回，都应遵守相应的访问范围。

质量评价要能够定位错误。一次错误回答，可能来自材料缺失、表格解析错误、对象关联错误、规则过期、召回遗漏，也可能是模型误用了正确证据。把这些原因混成一个满意度分数，很难指导改进。

因此，评价应覆盖知识加工、证据检索和最终任务结果。金额、日期、商品标识、配置字段等内容适合确定性比对；表达质量和证据支持度可以辅以模型评价，再由专家校准。Ragas 提供了多种评价指标，但评价工具仍需要业务标准才能发挥作用。

业务语义还应与动作连接。General Mills 的客户署名案例披露，约 200 张主数据和运营表进入 Ontology，系统结合约束、产能与成本提出供应链建议，超过 70% 的建议被人工接受。这个接受率来自整体应用的客户自报，不能等同正确率，也不能归因于某一个图谱算法。客户案例

Palantir 的产品机制提供了更具体的参考：对象关系映射业务数据，动作提交条件检查用户、参数和当前状态，语义变更支持审核与合并。对电商任务而言，这意味着知识可以解释依据，业务系统与规则服务则负责校验并执行操作。Ontology 架构、动作条件、变更审核

如何看待开源方案

开源项目处于不同层次，选型时需要先明确希望复用哪一段能力。

方案 值得重点考察的部分 需要关注的边界

OpenSPG/KAG Schema 约束、概念对齐、知识与原文互索引、逻辑检索 平台依赖、维护情况、本地模型效果及知识治理能力
LightRAG 图增强检索、跨文档关联和来源维护 抽取图的可信度、更新成本，以及精细授权
Microsoft GraphRAG 实体关系、社区摘要和全局主题综合 索引成本、更新删除机制；全局综合不能替代精确统计
Docling 结构化解析、中间表示和分块 真实材料的解析质量，以及后续语义治理
Dify 知识 Pipeline 可视化加工、测试与发布操作 与已有平台的职责重叠，以及许可证附加条件

RAGFlow 更适合作为知识加工与检索运营产品考察。研究时公开发布页同时存在 0.27.3 与 1.0.0-rc3，后者为候选版本，不能将主分支全部能力视为稳定承诺。版本说明

KAG 对知识结构化的参考价值较高，尤其是 Schema 如何约束构建、知识如何关联原文、精确查询如何与文本检索协作。研究时公开 Releases 的 Latest 为 2025-06-27 发布的 0.8.0；这一信息需要与维护情况一起考察，不能单凭发布时间判断项目状态。OpenSPG 的部署还涉及 Java、MySQL、Neo4j、MinIO 等依赖，应计入运维范围。KAG 发布说明、部署清单

LightRAG 和 Microsoft GraphRAG 则提醒选型者关注图知识的生命周期。LightRAG 的文档与实现显示，删除文档可能涉及共享实体关系重建及向量更新；Microsoft GraphRAG 的维护讨论也明确了增量更新对删除和修改的限制。具体能力仍需按固定版本验证。LightRAG 核心文档、GraphRAG 维护讨论

这里需要区分两种图：一种表达经业务确认的对象、关系和约束；另一种由模型从文档中抽取，用来帮助检索和综合。后者可以提供线索，但其中一条边的存在，并不能自动证明某项业务事实成立。

Dify 的知识流水线可以提供运营交互方面的参考。已有 Agent 管理平台的企业，需要权衡整体引入后的功能重叠；其许可证包含多 workspace 和前端标识等附加条件，也应按具体使用方式核对。许可证

这些方案可以形成研究短名单，无须同时部署。通用解析、检索和评价能力可以复用，企业仍需掌握自己的业务定义、来源映射、权限规则和验收案例。

让知识资产持续积累

电商企业可以选择增强文档知识库，也可以全面建设以本体和图谱为中心的平台。前者较容易起步，但难以独立承载实时状态、指标和跨对象规则；后者表达能力更强，建模与治理投入也更大。

更值得优先考虑的方向，是业务对象驱动的混合知识服务。它让文档证据、结构化语义和实时查询各自发挥作用，关系检索则在明确需要时引入。已有主数据、规则引擎、指标定义和业务接口，可以继续作为权威来源。

Google Cloud 在 2026 年 10 月 29 日的 Knowledge Catalog 发布中，也强调连接既有平台的语义定义、数据质量和血缘。这为复用已有语义资产提供了一个产品方向参考；页面中的效果数字属于厂商内部基准，不能直接作为其他企业的收益预期。官方发布

这种建设方式需要明确分工。架构师负责跨域概念与关系的一致性，业务责任人确认内容、适用条件和案例，技术团队提供加工、检索、评价与运营工具，原业务系统继续承担事实查询、规则判定和事务执行。各方共同维护一组真实业务问题，用它检验知识是否足以支持任务。

在资源安排上，可将结构解析、抽取和索引等批处理，与在线查询和生成分开。能够提前完成的加工放在知识发布阶段，在线路径只承担必要的过滤、查询、重排和推理。框架的接口兼容，也需要与模型、算子、运行环境的实际适配分别验证。

长期应保留的是原始证据、确认过的语义定义、业务评价样例与服务契约。向量、摘要和自动抽取图可以重建，但它们的生成版本及来源依赖必须可追溯。这样，模型和框架升级时，企业可以沿用已经积累的业务理解，再验证新的技术实现。

回到文章开头的优惠券问题：一个可靠的 Agent 应当说清商品与权益是否匹配，依据哪一版规则，还有什么条件尚未核实，并在获授权后调用正确的业务能力。知识底座的建设成效，最终应体现在这样的任务中——依据更完整，判断可校验，变更能够追踪，经验能够复用。
