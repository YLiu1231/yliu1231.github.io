AI 时代的软件基本功：Matt Pocock 对话 Uncle Bob

发表于 2026-09-09 分类于 Tech
当写代码成为廉价算力，软件工程的核心将从约束人的编码行为，转向约束 Agent 的产出系统。

一句话判断

这场访谈真正讨论的不是“AI 能不能写代码”，而是：当写代码从稀缺劳动变成廉价算力后，软件工程的核心从约束人的编码行为，迁移为约束 Agent 的产出系统；人的价值则上移到目标选择、架构分区、约束设计、异常识别与最终问责。

这也是 Uncle Bob 所说“基本功仍然重要”的深层含义：基本功没有消失，而是从程序员脑内的习惯，外化为可执行的 Harness、测试、依赖规则、评测门禁和组织训练机制。

核心观点：11 条关键判断

1. AI 生成很快，系统吞吐反而可能变慢

Bob 最初的真实困境是：Agent 写代码很快，却不断留下需要人清理的混乱；随着混乱累积，它开始修 A 坏 B、反复绕圈，人的总交付速度反而下降。

他重新启用了两类过去“有效但太昂贵”的工具：

  • CRAP：结合测试覆盖率与圈复杂度，评估函数或方法的变更风险；更准确地说，它不是笼统给整个项目打一个质量总分。
  • 变异测试：逐次、有控制地改动条件或运算符，再运行测试。若测试仍然通过，该变异体“存活”，说明测试没有识别这次行为变化；并不是“把全部逻辑同时反置后程序仍能运行”。

AI 带来的关键变化，是使这类高计算量、重复、枯燥的质量劳动第一次具备经济性。（约 05:15–14:55）

2. Lost in the Middle：上下文越长，不等于可用注意力越多

“中间会遗失”更准确的含义是：中部信息更容易被弱化或漏用，而不是物理消失。开头和结尾通常更容易获得模型注意；随着上下文增长，早期规则会被推入中部，遵从率下降。

其工程结论不是继续扩大上下文，而是：缩短初始 Prompt、只保留高优先级原则、按阶段重建上下文，并把不能遗忘的要求移出上下文。（约 14:00–16:20）

3. 用确定性机制取代指令累计

这条是访谈最关键的观点之一。Bob 发现，把每次失败都追加成一条 Prompt 规则，只会形成越来越长的“指导意见”；模型是否遵守仍是概率性的。

更可靠的结构是：

  • Prompt 表达目标与少量原则；
  • 测试、类型、指标和策略检查器给出不可协商的通过/失败；
  • Agent 在反馈 Loop 中反复修改，直到满足约束；
  • 人定义“什么叫正确”，而不是逐次提醒模型“请记得正确”。

也就是说，组织经验要从自然语言建议升级为可执行的质量控制面。（约 13:15–17:40）

4. Loop Engineering：用机器的速度余量换质量，而不是简单牺牲总效率

本文将这一机制概括为 “Loop Engineering”；这是分析术语，并非访谈中的正式命名。Bob 的机制是让 Agent 在确定性工具前循环，直到复杂度、覆盖率、变异测试和验收全部合格。

这确实会牺牲瞬时生成效率：一次五分钟的实现被拉长到一小时。但由于机器初始速度远高于人，团队可以把这部分速度红利用来购买过去负担不起的质量，并且仍可能快于人工半天。更精确的说法是：用局部速度换取质量与未来可变更性，目标是提高全生命周期总效率。（约 16:20–18:30，22:00–23:30）

5. 多 Agent 的两项收益与三类成本

多 Agent 的主要收益有两项：

  • 并行性：多个实现或检查任务可以同时运行；
  • 上下文可控：每个 Agent 只处理一个窄任务，完成后退出，新 Agent 以干净上下文接手，指令遵从和目标聚焦更好。

相应成本包括：启动与重新理解代码库的成本、Agent 之间的通信与交接成本，以及重复读取上下文带来的推理/Token 成本。如果分工没有带来并行、上下文隔离或独立验证中的至少一项，增加 Agent 数量只是增加编排税。（约 17:40–20:40）

6. 五阶段工作流：不是五个角色，而是五种证明义务

Bob 的原始对比是：单 Agent 约 5 分钟但结果可疑；多 Agent 流水线约 1 小时；人工约半天。他据此估计流水线仍可能有 4–5 倍效率优势。这是个人经验，不是受控实验。

五个阶段的准确输入输出为：

  1. Specifier：把人的需求转成 Gherkin（Given–When–Then）高层验收描述，以及从真实用户视角操作 UI 的 QA 流程。
  2. Coder：编写单元测试与生产代码，实现当前 Story，并使 Gherkin 验收场景通过；访谈没有说它输出新的 User Story。
  3. Cleaner：运行 CRAP 分析和代码审查，降低复杂度，清理实现阶段留下的结构问题。
  4. Hardener：执行变异测试，毫不妥协地发现测试覆盖不到的行为缺口。
  5. QA Agent：将 QA 文档转成可执行脚本，真实操作系统并产生确定性的端到端结果。

因此，多 Agent 的本质不是组织角色扮演，而是把“实现、清理、挑战、验收”这些容易互相妥协的责任拆开。（约 20:20–23:50）

7. 把人的价值观给 AI，照搬人的纪律多半是错的

Bob 在此作出访谈中最有新意的区分之一：

  • 价值观应该保留：可理解、低复杂度、行为可验证、依赖有边界、结果可验收。
  • 纪律不必照搬：例如严格逐行执行红—绿—重构，是针对人的短期记忆和行为偏差形成的工作方式；Agent 可能适合以函数或任务为更大粒度完成实现与测试。

正确做法是先找到一条工程纪律保护的底层价值，再为 Agent 重新设计实现机制与阈值，而不是机械复刻人的动作。（约 31:30–35:55）

8. 变更成本大幅下降后，昂贵的前置规划失去经济基础

这一判断不能推导成“不需要规划”。Bob 反对的是试图在执行前消灭全部不确定性：人的计划仍然不完整，Agent 只会更快、更忠实地放大错误假设。

当代码修改成本显著下降，更合理的方式是轻量对齐、小步实现、快速反馈、重新组织，再进入下一轮。便宜的是实现和修改，不是提前获得正确认知。（约 35:55–42:10）

9. Spec-driven 的关键不只在“有没有规约”，而在规约是否持久、如何获得权威

Matt 提出了一个重要判别点：一次性 Prompt、临时任务说明并不天然构成一种新范式；更关键的是规格是否被长期保存、持续回看并充当事实来源。

Bob 的回答更激进：他的需求规格是临时的，会不断变化并最终消失；人不再亲自写最终源码后，他倾向把运行结果、测试和工具约束视为更可靠的最终规格。因此真正应追问的是：

  • 规格是冻结的前置真理，还是随反馈演进的契约？
  • 需求、测试、运行系统发生冲突时，谁拥有最终解释权？
  • 哪些业务/合规规则必须长期保存，哪些实现规格可以临时化？

因此，无需过度纠结范式名称，但不能把所有规格都视为可丢弃；业务规则、安全边界和审计依据仍需持久化。（约 42:10–45:10）

10. 使用 Agent 之前，先做过 Agent 所承担的工作

Bob 的建议是：新人仍应先亲自写代码；进入大量使用 Agent 的公司后，先像 Agent 一样接受边界明确的战术任务，并受到同样的确定性门禁约束。经过数月实践、能识别混乱与失败轨迹后，才逐渐获得调度 Agent 的权力。

这个训练方案本身未经验证，但它揭示了真正的组织风险：如果战术工作全部自动化，战略判断赖以形成的经验回路也会被切断。不能只建立 Agent 生产线，还必须重建工程师的成长生产线。（约 45:45–53:00）

11. 编码基本功，是把复杂性驯化成可理解形态的能力

基本功的价值并不等于手写语法，而是通过命名、抽象、模块、接口、测试、依赖方向和反馈循环，把不可控的复杂性压缩成局部可理解、可改变、可验证的结构。这构成了全片的最终落点。

模型也是在有限上下文中工作，因此同样受益于这些结构。AI 只是把抽象层从编译器之上再次抬高，并没有取消复杂性。今天轻率丢掉的工程规则，往往会在系统规模扩大后以更昂贵的方式重新出现。（约 53:00–56:39）

这 11 条最终汇聚为同一个判断：Agentic Coding 的竞争力不在“生成更多代码”，而在能否把模型的速度转化成经过约束、独立验证、结构清晰且持续可演进的产出。
