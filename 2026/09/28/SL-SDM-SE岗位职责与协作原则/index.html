SL、SDM 与 SE：岗位职责、决策边界与协作原则

发表于 2026-09-28 分类于 Self-Learning
明确 SL、SDM 与 SE 在业务结果、项目交付和技术方案上的责任边界，以及授权、兼岗、探索评价和责任延续原则。

SL（Service Leader）、SDM（Service Delivery Manager）与 SE（System Engineer）分别承担组织与业务、项目交付、技术方案三个层面的责任。三者围绕同一目标协作，但各自负责的判断、决策和结果不同。

设置这些岗位，是为了明确责任、提高决策质量，并支持成员独立履职。评价岗位履行情况，应关注实际判断、行动和结果，而不是参会次数、材料数量或流程完成情况。

一、岗位定位

岗位 责任范围 核心职责
SL（Service Leader） 所辖业务与团队 确定目标与优先级，配置资源，对业务结果、团队成长和长期技术竞争力负责
SDM（Service Delivery Manager） 指定项目、版本或交付范围 组织执行，管理计划、依赖、风险与交付预期，完成验收和交接
SE（System Engineer） 所辖服务或技术领域 分析需求，设计与验证方案，解决关键技术问题，维护技术质量与资产

具体事项决定履职角色。同一人可以承担不同岗位，但应明确当前以何种角色作出判断、行使权限和承担责任。角色切换不免除已经承接的责任。

二、SL：业务结果、团队成长与技术发展的负责人

SL 既要保障当前交付，也要建设团队持续解决问题的能力。其职责包括业务判断、资源配置、人才培养和重大技术决策。

1. 明确目标与投入

理解业务场景，与相关方明确目标、预期价值、优先级及验收要求。统筹人力、预算和时间，平衡业务交付、技术探索、架构演进与日常维护，作出可兑现的资源承诺。

对探索性工作，明确目标场景、预期价值、投入上限、阶段检查点及继续或停止条件。对超出授权范围的资源和承诺，及时提交相应负责人决策。

2. 对业务与交付结果负责

向 SDM、SE 明确职责和权限，通过关键节点检查、专业评审和必要纠偏履行总体责任。授权后仍须关注结果，但应保留成员自主判断和执行的空间。

持续跟踪上线后的使用情况、业务效果与运行质量。价值假设发生变化、收益不足或需要追加投入时，与业务方决定继续、调整、收缩或停止。

3. 建设团队与培养人才

根据目标和能力需求配置人员，明确协作接口、关键岗位备份和人才梯队，降低关键能力对个人的依赖。

负责目标分解、绩效管理和成长辅导，依据可核实的工作事实评价贡献。鼓励主动协作、如实报告问题和基于证据开展讨论，不以单次延期、缺陷或探索失败直接判断个人能力与态度。

关注工作负荷和成员身心健康，避免兼岗长期超负荷。必要时提供支持或接管工作，同时明确范围及交还条件，帮助原责任人逐步独立承担职责。

4. 把握技术方向与长期竞争力

制定技术方向和阶段规划，识别关键能力差距，兼顾近期交付与长期发展。技术先进性应体现为适合业务的效果、效率、质量和成本优势，不能仅以技术新旧衡量。

SL 应具备评审重大方案的专业能力，理解关键取舍、验证证据和实施风险，对重大架构、长期投入以及自研、复用或引入外部能力作出判断，必要时参与关键攻关。

推动 AI 和自动化用于研发过程，以交付周期、缺陷、返工和实际节省投入验证收益，积累可复用的组件、工具、评测集、知识与工程方法。

三、SDM：交付组织与不确定性管理的负责人

SDM 将目标转化为可执行计划，协调各方完成交付。对于结果尚不确定的探索，负责组织验证、形成阶段结论并管理交付预期。

1. 组织端到端交付

明确交付范围、验收条件、任务分工、资源承诺、依赖关系、里程碑及观察期，组织需求、数据、算法、开发、测试、运维和业务等相关方协同执行。

在授权的资源、目标和验收边界内，决定任务安排、验证节奏及交付顺序。涉及业务优先级、资源投入或对外承诺变化时，说明影响并提交 SL 决策。

主动解决阻塞和依赖问题，对偏差提出并落实纠偏措施，不能以汇总进度代替交付管理。

2. 管理探索过程与交付预期

区分探索验证与正式交付。探索阶段承诺验证活动、阶段产物和可检查的结论，不将尚未验证的效果改善作为确定性交付承诺。

与 SE 明确假设、基线、验证方法及检查节点，将资源和时间落实到具体任务，控制并行尝试和重复投入。根据阶段证据调整计划，及时处理验证不足、结果冲突、投入超限和持续无进展等问题。

如实说明结果属于已验证可用、部分有效、假设被否定还是证据不足，同时呈现已投入资源、继续探索的成本及备选方案的交付影响，为后续取舍提供依据。

单次实验成功不等同于稳定可交付。SDM 应在证据充分后形成相应承诺，不保证探索必然取得正向效果。

3. 管理风险与质量过程

持续识别数据、模型、算力、接口、人员及跨团队依赖风险，明确责任人、应对措施和检查节点。

组织必要的评审、评测、测试和发布准备，核验功能质量、AI 效果、非功能要求的验证证据及交付内容完整性。专业结论由相应责任人作出。

将代码、数据、模型、提示词、知识库和关键配置纳入变更管理，关联版本、验证结果及发布记录。对遗留问题明确影响、规避措施和解决计划，组织灰度发布、生产观察、回退准备与异常协调。

流程完备不代表技术达标，交付管理职责也不自动包含最终发布批准权。

4. 完成验收、交接与改进

组织验收和观察期复盘，跟踪约定的业务效果与运行指标，推动未达标事项整改或明确后续责任人。

交付结束应以观察期、遗留事项承接和交接条件为依据，不能因项目关闭而中断责任。利用已有交付数据改进协作和质量管理，复用有效的模板、检查清单与实践经验。

四、SE：技术方案、验证证据与技术质量的负责人

SE 将业务需求转化为可实施、可验证、可维护的技术方案，并对专业判断和技术质量负责。

1. 分析需求与设计方案

理解用户任务、业务场景和约束，明确功能与非功能要求、系统边界、接口及技术验收条件，建立技术指标与业务效果之间的联系。

根据问题选择规则、传统算法、大模型、Agent 或组合方案，说明适用范围，以及效果、复杂度、成本和周期之间的取舍。

与相关方明确效果指标、基线、评测方法和异常场景。对重大不确定性，说明已知条件、待验证问题、验证方法及所需投入。

2. 负责架构与关键攻关

负责所辖领域的架构设计，明确数据、模型、服务和业务系统之间的关系，以及接口、任务流程、状态管理和依赖。

在授权范围内主导方案选择和技术评审，亲自承担关键设计、实验验证或核心实现，解决关键技术问题。

落实容量、时延、可靠性、安全、隐私、可观测性、恢复能力和成本要求。对 Agent，明确工具调用、权限边界、人工接管及失败恢复机制。

评估模型、框架、共享组件和第三方组件的适配性与维护风险，推进技术债务治理和架构演进。重大方案接受 SL 的专业评审；方案调整后，SE 仍须履行可行性判断、风险揭示及结果验证责任。

3. 组织实验与评测

提出有依据的技术假设，设计可复现的实验，建设基准集、边界场景和失败案例，防范数据泄漏与评测偏差，适用时通过线上实验验证实际效果。

识别大模型调优的不确定性，检查局部改善是否伴随整体退化，不以个别成功案例或单次运行证明稳定提升。

如实记录正向、负向和无结论结果，说明证据及局限，提出后续验证计划与备选方案。无法确定时明确原因，不作缺乏依据的确定性承诺。

SE 对判断质量、实验设计、验证证据和风险处理负责，不保证每次尝试成功。生产交付仍须满足适用的验收与发布要求。

4. 维护技术质量与资产

持续跟踪数据质量、训练与推理一致性、知识更新和模型行为变化，明确变更后的回归要求，分析并修复效果退化问题。

针对生成错误、工具误调用和敏感信息泄露等风险，设计检测、约束、降级与人工介入机制，并验证防护效果。

维护架构、接口、配置、性能基线、评测集和监控规则等技术资产，保持设计与实现一致。推动能力复用，明确使用边界和维护责任，对 AI 辅助产生的设计、代码和测试结果进行专业验证。

五、授权与协作原则

1. 区分业务决策、交付判断和技术结论

事项 SL SDM SE
新需求与资源投入 决定价值优先级和投入 评估范围、依赖及交付影响 判断可行性、技术成本和不确定性
一般技术方案 在关键节点检查，按需评审 检查交付约束与依赖 在授权范围内决策并验证
重大方向与架构 在授权范围内评审决策 说明资源占用和交付影响 提供方案、证据及取舍依据
未达标事项 决定资源与优先级，按授权处理例外 评估整改、范围调整或延期的影响 明确是否达标、风险及处理方案
持续优化 决定是否继续及投入边界 组织验证，管理阶段计划和预期 提出假设、验证效果并说明局限

资源或进度决策不能改变技术事实，未达标不能因交付压力被认定为已达标。验收条件调整须由相关责任方重新确认，发布和例外放行按相应授权执行。

2. 明确跨团队责任

跨团队项目须明确总体交付责任人，各团队负责人兑现约定的资源和交付承诺。项目统筹不替代各方的交付与技术责任。

分歧先由相关责任人协商；无法解决或超出授权时，提交具备相应权限的负责人决策。生产异常应按既有机制及时止损、恢复并同步信息。

3. 控制兼岗范围

原则上一人至多兼任两岗，其余职责须明确承接人。参与其他岗位的讨论，不等同于兼岗。

SL 开展专业评审、纠偏和必要支持属于本职。承担具体方案设计及实施验证，才构成兼任 SE；承担项目或版本交付管理，才构成兼任 SDM。

兼岗不扩大既有权限，也不免除必要检查。一般事项可自行检查，关键事项应由具备相应能力和授权的其他人员复核。复核权不等同于批准权。

4. 按影响与授权处理问题

在既定目标、验收要求、资源和技术边界内，影响局部、可验证、可回退的问题，由相应岗位自主处理。

出现以下情况时，应作为关键问题组织评估和决策：

  • 需要改变目标、缩减承诺或申请验收例外；
  • 预计超出资源或时间授权，挤占其他已承诺工作；
  • 涉及重大架构调整、跨团队接口变化，或影响难以隔离和恢复；
  • 关键指标超出约定退化范围，评测与实际表现冲突，或无法证明满足发布条件。

关键问题不必然由 SL 接管。应根据问题性质安排技术判断、交付评估、专业复核和资源决策，保留原责任人的履职责任。确需接管时，明确范围、原因及交还条件。

六、探索评价与责任延续

探索允许失败，但应有明确假设、合理方法、投入边界和阶段结论。处于约定边界内的单次失败或证据不足，不直接视为履职不到位；到达检查点仍无法形成结论、需要追加投入或影响交付承诺时，应重新评估。

对隐瞒负向结果、忽略整体回归、重复开展无依据尝试或超出授权未报告等行为，应检查相应岗位的履职情况。长期结果不足时，应复盘方向、方法、资源和能力，不凭单次结果评价个人。

项目或版本结束后，SL 持续负责业务价值与投入决策，SE 持续负责领域技术质量，SDM 按约定完成观察、遗留事项承接和交接。新项目或版本重新明确交付责任。

履职检查应使用已有计划、设计、代码、实验和复盘记录，避免重复汇报，不将检查项数量或单次实验结果直接换算为绩效评价。
